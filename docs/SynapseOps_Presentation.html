The Challenge

Why We Built SynapseOps

🔥
Manual Incident Response
Engineers spend hours diagnosing production issues — reading logs, correlating events, and identifying root causes manually. Mean Time to Resolution (MTTR) stays high.
⏳
Slow Code Review Cycles
Pull requests sit in queues waiting for human reviewers. No consistent risk assessment. Critical changes sometimes slip through without proper scrutiny.
💀
Pipeline Failures Block Teams
CI/CD failures require manual investigation. Developers context-switch to debug build issues, losing productive development time.
🎯
Risky Deployments
Deployments happen without awareness of current production health. No automated gate to prevent deploying into an already degraded environment.

The Core Problem: DevOps teams are reactive instead of proactive. By the time issues are detected, users are already impacted. We needed an intelligent system that monitors, analyzes, and acts — autonomously.

How Auto-Fix Works

1. Categorize & Parse
Regex-based error categorization + stack trace parsing to identify the exact file and line number
2. Fetch Source Code
Retrieves the actual source file from GitHub with ±15 lines of context around the error
3. AI Fix Generation
LLM generates fix with confidence score. Only proceeds if confidence ≥ 0.8 and category is auto-fixable
4. Create PR
Creates branch, commits fix, opens PR with root cause explanation — all via GitHub API

Natural Language Chat Interface

Ask questions about your infrastructure in plain English. The chat engine uses a 3-stage intent classification system to understand queries and fetch real data before generating responses.

Stage 1: Keyword Pre-Classification
Fast keyword matching against known terms (pod, cluster, pipeline, sla, etc.)
Stage 2: LLM Classification
Bedrock classifies the message with an intent guide, returning intent + parameters
Stage 3: Hard Override
If LLM returns generic intent but keywords match specific domain → forces correct intent

Data-Grounded Responses: The LLM only answers using actual data fetched from CloudWatch, DynamoDB, GitHub, or Kubernetes. It never fabricates information.

Data Layer

Database & Storage Design

All persistent data is stored in Amazon DynamoDB across 5 purpose-built tables, with Redis providing a fast caching layer with graceful degradation.

📋
synapse-ops-prs
PR analysis records — risk level, summary, review, diff analysis, priority, timing. PK: repo, SK: pr_number
🔄
synapse-ops-pipelines
Pipeline run records — workflow, status, AI failure analysis, auto-fix PR reference. PK: repo, SK: run_id
🚨
synapse-ops-alerts
Monitoring alerts — error spikes, traffic anomalies, SLA violations, predictive warnings. PK: ALERT#{api}, SK: timestamp
📊
synapse-ops-metrics
Time-series metrics — per-API snapshots, hourly rollups, error rates, latency. PK: METRIC#{api}, SK: timestamp
📝
synapse-ops-audit
Activity log + audit trail — agent events, auto-fix history, SLA checks, deployment gate decisions. Dual PK pattern.
🚦
synapse-ops-deployment-gate
Held deployments — status, hold reasons, traffic conditions, auto-release tracking. PK: HELD#{repo}, SK: run_id

Redis Cache Layer

  • Connection pooling (20 max connections)
  • Graceful degradation — all features work without Redis
  • Rate limiting via atomic Lua script
  • Webhook deduplication (24h TTL, SET NX)
  • Alert cooldown tracking
  • SLA target storage (24h TTL)
  • Monitored API list (30-day TTL)
  • Metric caching (120s–7200s TTL)

In-Memory Fallback

  • Activity log: 500-entry in-memory ring buffer
  • Dedup: bounded set (10K cap, evicts oldest half)
  • Rate limiting: fails open (allows requests)
  • DynamoDB init: background thread, non-blocking
  • Startup: loads last 24h from DynamoDB into memory

Reliability

Resilience & Security

Error Handling & Resilience

Exponential Backoff Retry
All external calls (GitHub, Bedrock, Teams) use configurable retry with jitter. 3 retries, exponential delay, per-service exception types.
Graceful Degradation
Redis down → in-memory fallback
DynamoDB down → memory-only activity log
CloudWatch empty → stream-scan fallback
kubectl missing → empty results
Teams webhook fails → logged, never blocks
Background Processing
All heavy work (PR analysis, pipeline healing) runs in daemon threads. Webhook returns 202 immediately. Thread failures are caught and logged — never crash the server.

Security Measures

🔐 Webhook Verification
HMAC SHA-256 signature verification on every webhook. Constant-time comparison via hmac.compare_digest().
🐳 Container Security
Non-root user (appuser) in Docker. No shell access in production. Health check via Python urllib.
✅ Input Validation
Pydantic validators on all config. Message length limits. API count limits. Query parameter bounds on all endpoints.
⚡ Rate Limiting
Chat endpoint: 30 req/min (configurable) via Redis Lua script. Atomic INCR + EXPIRE. Fails open when Redis unavailable.

End-to-End Workflow

Here's how SynapseOps handles the complete lifecycle of a code change — from PR creation to production deployment:

① Developer Opens PR
GitHub sends webhook → SynapseOps deduplicates → spawns background analysis thread
② AI Reviews Code (15-30s)
5 agents analyze diff, review code, assess risk → consolidated comment posted on PR
③ Conflict Detection
Checks for file overlaps with all other open PRs → warns developers to coordinate
④ Teams Notification
Adaptive Card sent with summary + Approve/Reject buttons → reviewer acts from Teams
⑤ CI/CD Pipeline Runs
If pipeline fails → AI analyzes logs → generates fix → opens auto-fix PR
⑥ Deployment Gate
Successful build on main → AI checks production health → PROCEED or HOLD decision
⑦ Production Monitoring
7 background jobs continuously monitor APIs → predictive alerts → SLA tracking
⑧ Chat & Dashboard
Team queries infrastructure via natural language → real-time dashboards show everything
