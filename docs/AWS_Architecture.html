🤖 1 · Amazon Bedrock

🤖

Amazon Bedrock bedrock-runtime

Core AI/LLM engine — powers all intelligent analysis across the platform

Amazon Bedrock is the AI backbone of SynapseOps. Every intelligent feature — root-cause analysis, auto-fix code generation, performance optimization suggestions, incident summarization, and the conversational DevOps chat — ultimately calls Bedrock's invoke_model API. The platform is model-agnostic and auto-detects the provider from the model ID to format the correct request/response schema.

Source Files

  • 📄 app/services/llm.py Singleton LLM client, all invocations
  • 📄 bedrock_client.py Root-level re-export wrapper
  • 📄 diagnose.py Connectivity diagnostic check
  • 📄 app/services/auto_fix.py Code fix generation
  • 📄 app/services/chat_engine.py Conversational chat
  • 📄 app/services/performance.py Optimization suggestions

📋 2 · Amazon CloudWatch Logs

📋

Amazon CloudWatch Logs logs

Primary data source — all API health, latency, traffic & error metrics are derived from CloudWatch

CloudWatch Logs is the primary observability data source for SynapseOps. The platform ingests structured application logs and runs CloudWatch Logs Insights queries to compute error rates, latency percentiles, traffic patterns, recurring errors, and incident timelines. A two-path design is used: Logs Insights first (preferred, has up to 30-minute indexing delay); if results are empty, a direct stream scan via describe_log_streams + get_log_events is used as a fallback.

Source Files

  • 📄 app/services/cloudwatch.py Core CloudWatchService class
  • 📄 app/services/log_analyzer.py Thin wrapper
  • 📄 app/services/error_analyzer.py Error rate monitoring
  • 📄 app/services/performance.py Latency / top APIs
  • 📄 app/services/incident_analyzer.py Incident timelines
  • 📄 app/services/sla_tracker.py SLA compliance
  • 📄 app/services/deployment_gate.py Pre-deploy traffic analysis
  • 📄 ecs/task-definition.json awslogs driver for app container

🗄 3 · Amazon DynamoDB

🗄

Amazon DynamoDB dynamodb resource

Persistent state store — alerts, metrics history, audit logs, PR & pipeline records, deployment gates

DynamoDB provides durable, serverless persistence for all operational state in SynapseOps. Tables are automatically created on first startup (BillingMode: PAY_PER_REQUEST) with a composite key design (pk = partition key, sk = ISO timestamp sort key). Every alert, metric snapshot, auto-fix action, PR analysis result, pipeline run, and deployment gate event is persisted here and survives application restarts.

Source Files

  • 📄 app/services/dynamodb.py DynamoDBService — core tables
  • 📄 app/services/deployment_gate.py held-deployments table
  • 📄 store.py PRStore + PipelineStore; auto-create
  • 📄 activity_log.py Audit table reads/writes

📦 4 · Amazon ECS / Fargate

📦

Amazon ECS / Fargate

Serverless container deployment for SynapseOps in ap-south-1

ECS Fargate is one of two production deployment targets. The task definition specifies a Fargate launch type with awsvpc networking, exposing port 5000. Application container logs are shipped directly to CloudWatch Logs via the awslogs driver. A Python-based health check polls /health every 30 seconds.

⚓ 5 · Amazon EKS

⚓

Amazon EKS (Elastic Kubernetes Service)

Primary production deployment platform via Helm chart; also queried at runtime via kubectl

EKS is the primary production target for SynapseOps. The Helm chart in helm/synapse-ops/ defines the Kubernetes deployment, service, and IRSA service account. At runtime, the K8sClient service runs kubectl shell commands to query live cluster state for pod health, node resource usage, service endpoints, and deployment rollout status.

🏗 6 · Amazon ECR

🏗

Amazon ECR (Elastic Container Registry)

Private Docker image registry for both ECS Fargate and EKS deployments

ECR hosts the synapse-ops Docker container image. Two separate ECR repositories are used — one per deployment region. The ECS execution role is granted pull access; the EKS nodes pull via the node IAM role.

🔐 7 · AWS IAM

🔐

AWS IAM — Roles & IRSA

Least-privilege roles for ECS task execution, ECS runtime, and EKS pod-level AWS access

Three IAM roles underpin SynapseOps security. ECS uses two separate roles following the principle of least privilege: one for control-plane operations (image pull, log shipping) and one for data-plane runtime API calls. EKS uses IAM Roles for Service Accounts (IRSA), binding a Kubernetes service account to an IAM role via OIDC federation.

🎬
ECS Execution Role

Used by the ECS control plane to pull the Docker image from ECR and ship container logs to CloudWatch Logs.

arn:aws:iam::127214194014:role/synapse-ops-ecs-execution-role
⚙
ECS Task Role

Assumed by the running container at runtime. Grants access to Bedrock (invoke_model), DynamoDB (CRUD), and CloudWatch Logs Insights.

arn:aws:iam::127214194014:role/synapse-ops-ecs-task-role
⚓
EKS IRSA Role

Federated via OIDC to the synapse-ops-sa Kubernetes service account. Provides EKS pods with the same AWS API access as the ECS task role.

arn:aws:iam::551494044780:role/synapse-ops-role

⚖ 8 · Application Load Balancer (ALB/ELB)

⚖

Elastic Load Balancing (ALB/ELB)

Internet-facing load balancer fronting both ECS and EKS deployments

An AWS Application Load Balancer (auto-provisioned by AWS) provides the public internet-facing entry point for SynapseOps. On ECS it is provisioned as part of the ECS service configuration; on EKS it is provisioned by the Kubernetes Service of type LoadBalancer defined in the Helm chart (helm/synapse-ops/values.yaml).

🪪 9 · AWS STS (Security Token Service)

🪪

AWS STS — Security Token Service

Used exclusively in the diagnostic script to verify AWS credentials are correctly configured

STS is used only in diagnose.py as part of the AWS connectivity check. It calls get_caller_identity to confirm that valid AWS credentials are present, and prints the account ID and caller ARN for verification. This is not part of the main application runtime path.

API Operationboto3 ClientPurposeFile
get_caller_identity sts Verify AWS credentials, print Account ID & ARN diagnose.py

🔄 End-to-End Data Flow

1
User Request / GitHub Webhook Arrives

A user opens the dashboard or GitHub fires a webhook (PR opened, pipeline run completed). The request hits the internet-facing load balancer.

ALB / ELB
2
Request Routed to SynapseOps Container

ALB routes the request to one of the running containers — either in ECS Fargate (ap-south-1) or EKS (us-east-1). The container image was pulled from ECR at startup.

ECS / FargateEKSECR
3
Log & Metric Data Fetched from CloudWatch

For any alert evaluation, performance analysis, SLA check, or deployment gate decision, the application runs CloudWatch Logs Insights queries against the monitored service's log group. Raw events are fetched directly if Insights has a delay.

CloudWatch Logs
4
AI Analysis via Amazon Bedrock

Structured log data, error summaries, or user chat messages are sent to Bedrock (invoke_model). Claude 3 Haiku returns natural-language root-cause analysis, code fix suggestions, or chat responses.

Amazon Bedrock
5
Results Persisted to DynamoDB

Alerts, AI-generated insights, auto-fix actions, PR/pipeline analysis results, and SLA metrics are written to DynamoDB for durability, history, and the activity feed.

DynamoDB
6
Response Returned (Dashboard / WebSocket / API)

Results are pushed to the user via REST API, real-time WebSocket updates, or as a webhook reply to GitHub/Teams. IAM roles (ECS task role or EKS IRSA) authorize all AWS API calls without any embedded credentials.

IAMALB / ELB

Services NOT Used

The following AWS services are not used by SynapseOps: S3, SQS, SNS, Secrets Manager, SSM Parameter Store, ElastiCache, Lambda, API Gateway. Redis is used for caching but runs as a standalone instance (not AWS ElastiCache). Teams notifications are sent via webhook (not SNS). GitHub integration uses direct REST API calls (not EventBridge).
